### Fixed
- **`[upstreams.resilience]` was unusable for the two keys it was introduced to carry (#144):** `applyDefaults` wrote `max_fails = 3` and `fail_timeout = "10s"` into the *deprecated* upstream-level fields whenever they were unset, and validation then saw a value in both places and rejected the configuration for "setting both spellings" — of keys the operator had written exactly once, in the position the migration told them to use. Every configuration following the documented migration failed to start. The defaults are no longer materialised; they are applied at the point of use by `CircuitMaxFails`/`CircuitFailTimeout`, which is also the only way the new `sources` field in the resilience API can honestly say where a value came from: a default written into the struct is indistinguishable from one an operator set. Introduced in #143, by the same hand that is removing it. `TestResilienceSpellingIsUsableOnItsOwn` was verified to fail against the defect, and `TestDeprecatedCircuitSpellingStillWorksAndConflictsAreStillRejected` pins that the old spelling still works and that genuinely setting both is still an error.
- **The documented default for `max_fails` was wrong again, in the other direction (#144):** #143 changed the value contract, `docs/getting-started.md` and `docs/core-http.md` to say the default is 1, on the strength of `DefaultMaxFails = 1`. That constant was unreachable for any configuration parsed from a file, because the parser materialised 3 before it could ever be consulted — so every real deployment has always used 3, and the "correction" made the documentation less accurate than it had been. The constant is now 3, matching the behaviour every deployment already has, and the docs say 3. No runtime behaviour changes.
- **`GET /api/apps` ignored `[upstreams.resilience].max_fails` entirely (#144):** the projection read the deprecated field directly, so an operator who migrated to the new spelling saw the old value — or, once defaults stopped being materialised, a zero. It now resolves through the same accessor the runtime uses, so the Console reports the value actually in force.

- **An open circuit on an auth dependency was never proven to fail closed (#143):** the forward-auth and JWKS pools had fail-closed tests for admission rejection and for an unreachable service, but the circuit breaker added in #294 is a *new* way for those dependencies to be unavailable, and a new refusal path is exactly where a fail-open gets introduced without anyone noticing. `TestForwardAuthFailsClosedWhenTheCircuitIsOpen` and `TestJWTFailsClosedWhenTheCircuitIsOpen` now drive `Authenticator.Wrap` against a healthy auth service whose pool circuit is open, so nothing but the circuit stands between the client and the protected handler, and count invocations of that handler rather than trusting a status code. Both were verified to fail when the dependency is made to fail open.
- **The value contract recorded the wrong default for `max_fails` (#143):** it documented "omitted/zero defaults to 3" where the code has always used 1, and `docs/getting-started.md` repeated the same wrong number. Both now say 1. `docs/core-http.md` also still listed "no circuit breaker" as a limitation after #294 shipped one; the limitation is now stated accurately as the absence of *outlier ejection*.

- **The admission fuzz asserted an invariant it could not observe (#292):** `FuzzAdmissionInterleavings` checked `sum(A_b) <= A_p` from a concurrent reader that samples `Active()` and then walks the per-backend counters. Those are independent lock-free counters, so a request admitting and picking between the two reads makes the sum exceed an already-stale active count while no instant ever violated the invariant — the assertion was testing its own sampling. It fired once under heavy parallel load and would have become an intermittent CI failure. The cross-counter invariant is now asserted at quiescence, where it is exact and where a leaked slot still shows up; the single-counter invariants stay checked throughout. Introduced in #287 by the same hand that is removing it.
- **Active health could take a whole stream route down (#286):** the checker defaults to `http` and an HTTP probe issues a `GET` to a path, so a stream route fronting Postgres, Redis, MQTT or SMTP that shared an `[[upstreams]]` block with `health_check.enabled = true` failed every probe, flipped every backend to unhealthy — which backend eligibility honours — and took the entire route out of service. Stream routes now force the probe type to `tcp`, a pure reachability check and the only honest probe for a protocol-agnostic proxy, and UDP-only routes get no checker at all because a UDP backend does not answer a TCP dial. The upstream's own `type` still governs its HTTP pool, which is a different object, so no configuration change is forced on anyone; the visible consequence is that an upstream used by both surfaces is probed once per pool.
- **Every FastCGI handler generation leaked a goroutine and an open backend connection (#285):** `gofast.NewClientPool` spawns a `for { c := clientFactory(); pool <- c }` producer over an **unbuffered** channel, and `SimpleClientFactory` dials eagerly — so that goroutine sat blocked on the handoff holding a live connection to the application server. `ClientPool` has no `Close` and no stop path, the handler retained no reference to it and, unlike `proxyHandler`, had no `Close` of its own, so it was never generation-staged. With N such locations and M reloads that is N×M idle connections and goroutines held for the life of the process. The pool is gone: connections are dialled per request from the selected backend and closed when the request ends. Nothing was lost by removing it — created with `scale = 0` its channel was unbuffered, so it never actually reused a connection; it only ever pre-dialled one and leaked it. `TestFastCGIHandlerGenerationsDoNotLeak` builds and retires fifty generations against a real listener and asserts that **zero** connections were opened and the goroutine count is flat.
- **`fastcgi_pass = "<name>"` silently dialled the TCP host "name" (#285):** the address parser's default branch treats anything without a recognised prefix as a TCP address, and validation only checked the field was non-empty, so naming an upstream that did not exist produced no configuration error and failed at runtime instead. A target must now be a configured upstream name or an unambiguous address, checked at validation for both `fastcgi_pass` and `uwsgi_pass`.
- **A stream protocol switch no longer retires the running listener to free its port (#269):** the fix proposed for the Windows `internal/stream` flake made `Reload` shut down the existing same-address listener before binding the new protocol, on the premise that TCP and UDP share a port namespace under Windows Enhanced Socket Security. That premise is wrong on every supported platform. Linux hashes the two protocols in entirely separate bind tables (`udp_table` versus `inet_hashinfo->bhash`), and the Windows CI log disproves it directly: `TestStreamProtocolSwitchBindFailureIsAtomic` binds UDP over a port a TCP listener already holds and that bind *succeeds*, which is why the test reaches its assertion at all instead of skipping. Retiring first cost three things and bought nothing — it forfeited the atomic rollback guarantee, so a failed reload left the address serving nothing; it destroyed a listener the candidate configuration explicitly *kept*, silently and without an error, whenever a configuration ran TCP and UDP on one address; and it orphaned that listener's freshly built route, leaking its upstream pools and their health-check goroutines on every such reload. `Reload` binds before it retires again, on all platforms, and `TestStreamSameAddressBothProtocolsCoexist` now pins the coexistence property that the change violated.
- **Protocol-switch tests draw ports from outside the ephemeral range (#269):** the real cause of the flake was never a shared namespace but the `freeTCPAddr`/`freeUDPAddr` idiom, which binds `:0`, reads the port and closes — a reservation that only holds in *one* protocol's table. Because the two tables are independent, a UDP listener holding port P does not stop this same process's own outbound TCP connection from being assigned P as its source port, and the later TCP bind then fails with `EADDRINUSE`. `SO_REUSEADDR` cannot rescue it: `inet_bind_conflict` waives the conflict only when *both* sockets set it, and Go sets it on listeners but not on dialled sockets. Nor does waiting, since the squatter may be a live connection or sit in a 60-second `TIME_WAIT`. The new `reserveSwitchAddr` helper takes a port from a band below every platform's ephemeral range, so the kernel can never hand it out as a source port, and proves it bindable under *both* protocols before returning — which also sidesteps Windows' per-protocol excluded port ranges, where a bind inside a reserved block fails with `WSAEACCES` rather than `EADDRINUSE`.
- **The console-e2e `/api/config/rollback` `409` flake is a legitimate, retriable conflict, not test-suite bit rot (#270):** the coordinator rejects an apply/rollback whenever the live handler-generation advances past the value the admin handler observed at authorization time — by design, so an async reload cannot be silently outrun. That generation also advances for a reload the file watcher fires for its own echo of an immediately preceding admin write, best-effort suppressed by a digest match rather than guaranteed (`R10-01`), so a rollback issued right after an apply can race that echo and see "the live runtime changed" even though nothing about its content actually conflicts. `TestCoordinatorLiveGenerationConflictIsNotContentAware` reproduces the mechanism deterministically, and `real-server.spec.ts`'s rollback test now retries a `409` instead of failing on the first one, matching how a real client is expected to handle it.
- **`golangci-lint`'s SA5011 no longer flags the `if x == nil { t.Fatal(...) }` idiom in tests (#270):** `t.Fatal`/`t.Fatalf` terminate the calling goroutine via `runtime.Goexit()`, but `staticcheck` doesn't always recognize that, so it intermittently reported a "possible nil pointer dereference" on the very next line for whichever handful of the idiom's 100+ existing call sites it happened to analyze in a given run — a moving target that made the pre-push gate flaky rather than actually actionable. `.golangci.yml` now scopes `SA5011` out for `_test.go` files only; production code keeps the full check.

### Changed
- **Backend health is reported as a five-state enum instead of a boolean, and pools carry a server-computed verdict (#144):** `BackendProjection.healthy` and `BackendStatus.Healthy` were booleans, so every reason a backend could be out of rotation collapsed into "unhealthy" — or, worse, into "healthy", because the boolean was only ever fed by the *health checker*. A backend whose circuit had tripped, or one already at `max_active_per_backend`, was still reported healthy while receiving no traffic, which is precisely the state an operator is trying to diagnose. The field is now `state`, one of `available`, `circuit_open`, `circuit_half_open`, `health_unhealthy` or `at_capacity`, absent when nothing live has been observed; the Console renders each distinctly rather than as a green or red dot. `AppProjection` also gained `verdict` (`healthy`/`degraded`/`down`/`unknown`), rolled up on the server rather than in the browser so the Console and any API client cannot disagree during an incident (ADR 0014) — a pool with one available backend and one tripped one now reads `degraded` instead of letting the healthy backend mask the tripped one. `unknown` stays distinct from `down` throughout: not yet observed is not the same as observed to be failing. This is a breaking change to `GET /api/apps` and `GET /api/upstreams`, recorded in `docs/compatibility.md`. Because `internal/admin` deliberately does not import the runtime and receives these values as plain strings, the enum could drift silently; `TestAdminBackendStateLiteralMatchesTheUpstreamEnum` and `TestAdaptUpstreamsPassesEveryBackendStateThroughVerbatim` in `internal/app`, the only package that imports both, pin the wire strings to `upstream.BackendState`, and the first was verified to fail when the literal is changed. The `/api/apps` E2E previously ran against a config with no upstreams at all, so it parsed an empty array and asserted nothing about backends; the E2E config now carries a routed pool and the test asserts the projected state and verdict.

- **Client cancellation is recorded as 499 instead of 504 (#144):** `proxyErrorStatus` mapped `context.Canceled` and `context.DeadlineExceeded` to the same 504, so every client that hung up was counted as a gateway timeout. Nothing is transmitted either way — by then the client is gone — but the recorded status is what dashboards are built on, and inflating "gateway timeout" with requests where nothing timed out corrupts exactly the signal an operator reaches for during an incident. Telling the two apart is not a matter of taste: `context.Canceled` arrives from a client going away *and* from Jul's own retry deadline, which derives its context from the inbound one, so without checking the inbound request context specifically, Jul's own deadline enforcement would now be reported as clients disconnecting. A genuine upstream timeout and an exhausted retry deadline both remain 504.

- **`jul_upstream_healthy{pool,backend}` is retired in favour of `jul_upstream_backends_healthy{pool}` (#144):** the `backend` label was a raw dial address, so a pool's series count grew with every Kubernetes pod that had ever backed it and never shrank — contradicting the project's own bounded-label rule, and in a metric that exists to tell an operator whether a pool is healthy. The replacement is a count; per-backend verdicts move to the Admin API, which answers on demand instead of retaining a series per address forever. This is a deliberate compatibility break on a released metric, recorded in `docs/compatibility.md` and in an explicit `retiredReleasedMetrics` list rather than by loosening the frozen v1.32.0 baseline, which still holds every other released family exact.
- **Pool metric series are now retired when a pool leaves (#144):** `pool` labels are bounded at one configuration snapshot but not over the life of a process, and `upstream_add`/`upstream_remove` are supported admin patch operations, so pool-name churn was an operator-reachable leak rather than a hypothetical one — already affecting `jul_upstream_backends`, `jul_discovery_errors_total`, `jul_upstream_probes_total` and `jul_upstream_probe_duration_seconds`. `Registry.Commit` now reports each departing pool identity and every `pool`-labelled vector deletes it. Retirement is keyed on the pool *name*, not the `(name, scheme)` key that owns the pool object: one name can serve both an http and an https pool, and retiring on the key would have deleted series the surviving sibling was still writing. `TestPoolSeriesAreRetired` churns 2000 pool names and asserts the gathered series count returns to the surviving pool's own; without the fix it reports 12006.

- **`max_fails` and `fail_timeout` moved into `[upstreams.resilience]` (#143):** they are the circuit breaker's failure threshold and open duration, so leaving them at the upstream level made the resilience block most of the resilience surface rather than all of it. Same names, same defaults, same meanings — only the position changed, and the migration is moving one line. The old top-level spelling stays valid and is scheduled for removal in the next major. Setting a threshold in both places is a validation error rather than a precedence rule, matching how `proxy_retries` and `retry_attempts` are already handled: a configuration that means one of two values depending on a rule nobody remembers is worse than one that refuses to start.
- **`Pool.MarkSuccess` no longer writes on the healthy path (#143):** it performed two unconditional stores on *every* successful request. With the breaker's generation gate it is two atomic loads and no store when the generation still matches and nothing is on record — `BenchmarkMarkSuccess` measures **1.69 ns/op, 0 allocs**.

- **A recovering backend no longer takes the full production load the instant its cooldown ends (#294):** `max_fails` and `fail_timeout` were already a circuit breaker in everything but name, but the state between OPEN and CLOSED was implicit — `available()` simply compared `downUntil` against the clock. Every request in flight when the cooldown elapsed evaluated that comparison independently and every one of them answered yes at the same instant, so a backend that had just come back was handed the entire waiting load, which is a good way to knock it over again. Under `least_conn` it was worse: the recovered backend has nothing in flight, so it looked like the *best* candidate for every request. There is now an explicit `CLOSED`/`OPEN`/`HALF_OPEN` state machine per backend, and the new `circuit_half_open_probes` (default `1`, explicit `0` for the old unbounded behaviour) bounds how many requests may test it. The bound is exact under contention, not approximate: eligibility is a non-consuming filter so the balancer still chooses, and only the chosen backend is asked to claim a probe slot, with re-selection if that claim loses the race. `max_fails` and `fail_timeout` keep their names, their defaults and their meanings.
- **Retuning `max_fails` or `fail_timeout` no longer forgets which backends are out of rotation (#294):** both were part of `upstreamMeta`, the set of fields that define a pool's identity, so changing either rebuilt the pool, restarted its health checker and discarded every backend's failure state. That put all of the ejected backends back under full load at once — during a reload, which is precisely when an operator is reaching for those knobs *because* backends are failing. They are now applied to each backend in place, preserving circuit state, failure counts and any probe already in flight, and their lifecycle disposition records this.
- **A late result can no longer clear failures it knows nothing about (#294):** every admission now carries the circuit generation that authorised it, ordinary requests included, and results are checked against it under the lock. Without that, a request admitted before a backend failed could complete after it had opened, been probed and recovered, and its stale success would reset a failure run belonging to a later generation — or its stale failure would count toward one. The same token is what stops a hung probe, which may legitimately be a multi-hour gRPC stream, from closing a circuit that has since re-opened.

- **A backend weight change no longer resets that backend's runtime state (#285):** `UpdateBackends` reused a `*Backend` only when address **and** weight matched, so a Consul or DNS-SRV weight flap silently discarded its in-flight accounting and passive failure history — precisely when an operator is watching them. `Backend.Weight` becomes an unexported `atomic.Int64` behind a `Weight()` accessor, which costs nothing because the only hot-path readers are two lines in `weightedRR.pick` that already hold that balancer's own mutex; the reuse key drops to the address alone, and a changed weight is applied in place. `weightedRR.updateBackends` now clears its current-weight map rather than pruning departed entries, so smooth weighted round-robin re-converges immediately instead of carrying an accumulator earned under the old weight.
- **`backend_tls` is reclassified from `restart_required` to `hot_reload` (#140):** the promotion is earned, not asserted. The HTTP proxy, native gRPC and the transcoder build their clients with the handler generation that owns them, and the resolved policy's **fingerprint is now part of the upstream pool's identity**, so a changed policy rebuilds the pool and with it the probe client — the last consumer that would otherwise have kept its startup trust. Because the fingerprint digests file *contents*, rotating a certificate in place with no configuration edit changes the pool identity and is applied on the next reload; detection and action are now the same thing for this field, where they were deliberately separated while the consumers were still being wired. A malformed policy still fails during candidate preparation, so the reload aborts before anything is published. One consequence worth knowing: a policy change rebuilds the pool, so its balancer and health state restart — the same behaviour a health-check settings change has always had.
- **`jul lint` now fails on an error-severity finding without `-strict` (#137):** `Lint()` gained its first `SeverityError` diagnostic — `insecure_skip_verify`, which turns a verified backend connection into an unverified one — and the command exits 1 for it, counts it as an error in the summary, and reports it even under `-quiet` (which suppresses warnings, as its help always said). `Validate()` still accepts the field, and `jul check` still passes: a field whose entire purpose is opting into an insecure mode cannot be a validation rejection, or the emergency path it exists to provide disappears. Self-contradictory combinations remain hard errors — the bypass with `peer_identities`, or with a non-system `ca_mode`. The server also logs one warning per affected backend at startup, and the Console security projection carries bounded counts; no metric label carries an upstream name.
- **New lint warning for an unverifiable health target (#137):** an `https` pool with an enabled HTTP probe and no `backend_tls` block is reported, because probes verify against the platform trust store alone. This ships several releases before health probes adopt the resolved policy, at no cost, so the gap is visible early.
- **`docs/health.md` corrected (#137):** it stated that active probes use `InsecureSkipVerify: true` "by design". That was never true of the shipped code, which sets no `TLSClientConfig` at all and therefore verifies against the system roots. The document now describes what the code does, and the correction is called out rather than quietly applied.
- **New `config:trust` permission (#259):** changing a listener's trusted-proxy policy now requires its own grant, held by no predefined role except `admin`, and is recorded under its own audit category `config.client_address` so a trust-boundary change is greppable. The check is on the effective configuration difference rather than on the endpoint used, so the general structured patch surface cannot be used to route around it — an operator with `config:write` and `config:apply` can change everything else and not this.
- **Access-log fields `remote` → `client_ip` + `peer_ip` (#136):** the single `remote` field was ambiguous about whether it meant the end client or the socket peer, so it is removed rather than repurposed. Every record now carries `client_ip` (the canonical client) and, only when a trusted proxy made them differ, `peer_ip` (the direct transport peer) — the same "omit what adds nothing" rule already used for `trace_id`. `AccessRecord.Remote` is renamed to `Client` with a new `Peer`, and the Console Operations Log tail projects `client_ip`/`peer_ip` under those names, rendering them as `client via peer` when they differ. No compatibility alias ships: there is no adopted deployment to protect, and keeping one would have made the ambiguity permanent.
- **Outbound `X-Forwarded-For` is rebuilt, never appended (#136):** both the HTTP reverse proxy and the native gRPC proxy now emit `X-Forwarded-For: <canonical client>, <direct peer>` constructed from Jul's own trusted context, with the peer omitted when it equals the client. An inbound chain is never preserved, so an untrusted sender's assertion cannot reach a backend: `client, P1` received from peer `P2` is emitted as `client, P2`, deliberately dropping intermediate trusted hops rather than re-injecting third-party data into a channel the backend authenticates. Custom `headers` still apply after construction, so an explicit operator value wins — and only an operator can set one. `$proxy_add_x_forwarded_for` is redefined in place to the same chain; `$remote_addr` is the canonical client (matching NGINX with its realip module, which is exactly what `client_address` expresses) and the new `$realip_remote_addr` carries the direct peer under NGINX's own name for it.
- **The WAF sees the canonical client (#136):** Coraza derives `REMOTE_ADDR` inside an unexported request processor with no injection point, so Jul wraps the engine behind `experimental.WAFWithOptions`, reads the identity from the transaction's context, and returns a transaction overriding only `ProcessConnection`. Rules behind a declared trusted proxy therefore match the end client rather than the proxy — with no `RemoteAddr` mutation, no fork of the 297-line response interceptor and no upstream dependency. It also bypasses Coraza's `strings.LastIndexByte(':')` address split, so an IPv6 client reaches rules in the same normalized form as an IPv4 one.
- **`middleware.ClientIdentity` is renamed to `middleware.PeerCertIdentity` (#135):** the mutual-TLS certificate identity and the new client *address* identity are different concepts, and the old name made documentation ambiguous. `WithClientIdentity`/`ClientIdentityFrom` become `WithPeerCertIdentity`/`PeerCertIdentityFrom`. This is an internal package rename with no configuration or wire-format change; `$ssl_client_*` variables are unaffected.
- **Phase 5 structured-configuration closure (#82 / PR #255):** completed exact `listen + server_names` targeting for server-level typed operations, with ambiguous legacy listen-only operations failing closed on shared listeners; aligned server limits, HTTP/3, and h2c toggles with the same exact targeting; captured the value-free pending-restart snapshot before structured preview and rejected stale handoffs when staged state or base version changed; kept optional-projection compatibility fail-closed by disabling unavailable controls rather than inventing defaults; proved real-server typed create, change, stage, update, discard, delete, and rollback flows through the browser and data plane; removed the obsolete Issue-81 one-shot workflow/bundle and dead compression/global-rate-limit TOML helpers; refreshed embedded Console assets; and serialized only the shared mutable real-server Playwright project. This closes Phase 5 without claiming universal hot reload, dynamic cache-backend replacement, or newly authored operator guidance.
- **Complete runtime preflight chain:** lean builds no longer return immediately after a successful WAF capability check. Structured and raw validation now continue through auth construction and compression build-tag dry-runs, so missing htpasswd files and unavailable `br`/`zstd` encoders fail closed before persistence or staging.
- **Closed-world configuration lifecycle authority (#89):** the Go registry in `internal/lifecycle/registry.go` is now the sole machine authority for how every configuration field behaves across a reload, and the schema is closed-world. A new reusable inventory, `config.SchemaPaths` / `config.SchemaLeaves`, is the single reflection over the TOML schema: it represents every dynamic collection key — array-table index, plugin name, RBAC principal, map key — as the canonical wildcard `*`, handles pointer blocks, nested array tables, scalar maps, `Duration`/`Size`/`time.Time`, and is deterministic and build-tag independent. All 224 public leaves of that inventory now carry exactly one disposition, with no exemptions. `lifecycle.FieldClass`, which returned `hot_reload` for an unregistered path, is removed: `lifecycle.Lookup` returns `(Entry, bool)` and `lifecycle.ClassOf` returns an error naming the regeneration command, so a newly added startup-consumed field can no longer be persisted and reported as applied while the running process keeps the startup value.
- **Exact lifecycle leaves instead of coarse groups (#89):** the grouped `servers.*.tls` and `servers.*.http3` entries are split into exact leaves — `tls.enabled`, `.cert`, `.key`, `.min_version`, the `client_auth` mode/CA/SAN/CRL bundle, every ACME leaf, `http3.enabled` and `.alt_svc_max_age` — so a restart reason names the field that actually changed rather than a whole subtree. Splitting preserved same-path file-content detection: certificate, key, client-CA and CRL material is still digested by file content, so rotating a file in place without editing the configuration is detected. Admin, cache, observability and global fields are likewise classified per leaf. Classification records proven behavior only: cache settings remain restart-required until #92/#93, static certificate material until #100, access-log sinks until #98, and tracing stays restart-bound.
- **Truthful ignored and reserved dispositions (#89):** `global.access_log`, `global.error_log`, `servers.*.access_log` and `servers.*.error_log` are `ignored_deprecated` — parsed for v1 compatibility, read by no runtime consumer, never a pending restart, and never reported as applied. A new `validation_rejected_reserved` class covers `servers.*.tls.acme.dns_provider` (DNS-01 is unimplemented and rejected by validation, while the supported `http-01` and `tls-alpn-01` selector remains an ordinary setting) and `servers.*.locations.*.rate_limit.max_conns` (connection caps are listener-global and rejected at location scope).
- **`stream.*.protocol` is hot-reloadable (#89):** switching an L4 listener between TCP and UDP on the same numeric address no longer requires a restart. An L4 listener is keyed by protocol and address, and the reload binds the candidate protocol's socket before mutating any live state, so the switch is a transactional remove/add. Established TCP connections and tracked UDP sessions follow the retired listener's drain boundary while new traffic uses the candidate protocol; a candidate that cannot build its routes or bind its socket leaves the previous protocol serving. Proven by a real-socket characterization matrix in `internal/stream/protocol_switch_test.go`, including both transition directions, route-build and bind failures, established-connection drain, UDP session retirement, repeated switches, goroutine-leak and race lanes.
- **One conditional classification service (#89):** `lifecycle.Classify(before, candidate, live)` is a pure, side-effect-free classifier that resolves the entries whose disposition depends on the live listener set — a bind-time value edited on a retained address is restart-required, the same edit confined to an address the reload adds or removes is adopted at bind. Reload gating, managed apply preflight, planned restart, diff projections and the Phase 5 preview API consume it, so preview and apply cannot disagree. Its results are bounded: canonical paths, closed class names, bounded subsystem identifiers and fixed reason text only. `lifecycle.DiffEntry` no longer carries before/after values, and secret-bearing paths (`admin.token`, RBAC principal tokens, discovery tokens, TLS material) are compared as digests.
- **Generated, drift-gated lifecycle mirrors (#89):** `docs/config-lifecycle.yaml` is no longer hand-maintained; it, `docs/generated/config-lifecycle.md` and `docs/generated/config-lifecycle.json` are deterministic renderings of the Go registry produced by `go generate ./internal/lifecycle` (`make lifecycle-generate`). Generation is sorted, network-free and free of timestamps, absolute paths and map-iteration order. New `make generated-check` compares the rendered bytes, writes nothing, and fails with the exact regeneration command; it runs as part of `make ci-pr`. `scripts/docs-check.py` no longer reimplements lifecycle semantics — it consumes the generator's check mode and the generated metadata, keeping only structural assertions.
- **Duplicate lifecycle field lists removed (#89):** `CacheRestartRequired`, `EgressRestartRequired`, `AdminRestartRequired`, `MetricsRestartRequired`, `LogFormatRestartRequired`, `TracingRestartRequired` and `AccessLogRestartRequired` are deleted — each enumerated fields the registry fingerprint already compares, and none had a production caller. `scripts/dump-schema-leaves.go` and `scripts/dump-lifecycle-registry.go` are removed in favour of the reusable inventory API and the generator. `internal/server.listenerBindFingerprint` remains the socket-level comparator but is now a checked mirror: a test asserts every property it freezes maps to a registry path classified as listener-bound, and that a new listener-bound entry is added to that mapping.
- **Spurious stream-protocol diff fixed (#89):** an omitted `[[stream]] protocol` means `tcp`, but the schema-derived extractor compared the raw value, so a document that spelled the default out was reported as a change. The extractor now normalizes the default.
- **Shared-cache HTTP conformance and unsafe-method invalidation (#132):** the response cache now implements the RFC 9111 / RFC 5861 shared-cache contract instead of approximating it from a lossy header subset. Request `Cache-Control: no-store` bypasses lookup and storage without purging what another client stored; request `no-cache`, `max-age=0` and the HTTP/1.0 `Pragma: no-cache` fallback force **successful synchronous validation** before any reuse, however fresh the entry is. Response `no-cache` is now **stored** — that is what lets a `304` save the body — but marked so that every reuse validates first; a field-qualified `no-cache="Header"` is conservatively treated as whole-representation validation. `private`, `no-store` and `Set-Cookie` responses are not stored; `public`, `s-maxage`, `max-age`, `Expires`, `must-revalidate`, `proxy-revalidate`, `stale-while-revalidate` and `stale-if-error` are parsed once at publication and recorded on the immutable entry. `must-revalidate`/`proxy-revalidate` now genuinely forbid stale reuse, outranking both `[cache] stale_while_revalidate` and `[cache] stale_if_error`; an explicit response `stale-if-error` replaces the global setting in both directions, including an explicit `0`. Freshness is measured from the origin's own `Date`/`Age` (RFC 9111 §4.2.3 corrected initial age) rather than from arrival, so a response that already aged in an upstream cache is no longer served for a full fresh lifetime. The directive parser is total: multiple field lines merge, tokens are case-insensitive, quoted values may contain commas, duplicates resolve to the smallest lifetime, malformed and negative arguments resolve to zero, and out-of-range arguments clamp upward per RFC 9111 §1.2.2.
- **Mandatory validation reuses the #131 revalidation seam (#132):** synchronous validation joins the existing generation-keyed call state rather than adding a second singleflight, so concurrent validators for one (effective key, generation) produce exactly one origin request. The leader runs on the generation's background lease, so it is bounded by `[global] shutdown_timeout` and is not cancelled by its own client; a waiter that gives up cancels only its own wait. Every leader and waiter terminates on every outcome — `304`, a new representation, an uncacheable response, an origin error, a timeout, a cancellation and a panic — with no call state stranded and no panic value reaching a waiter, a log or a metric. Conditional requests follow RFC 9110 §13.1.2 validator precedence (`If-None-Match` when an entity tag exists, `If-Modified-Since` otherwise, never both) and replace any conditional header the client sent. With no validator, or with no generation-lease seam installed, validation degrades to a complete origin fetch — never to serving an unvalidated entry.
- **Correct `304 Not Modified` metadata merging (#132):** a `304` now produces a new immutable entry that atomically replaces the stored one, preserving the stored body and status while replacing end-to-end fields the origin supplied, removing obsolete `Warning` fields (RFC 9111 §5.5), and never merging hop-by-hop fields, anything named in the `304`'s `Connection`, or `Content-Length`. Freshness, validators and the entire policy set are recomputed from the merged headers, so an origin can tighten its policy through a `304` and have it apply immediately. A `304` that makes the representation unstorable, or that **changes `Vary`**, discards it and re-fetches, because publishing it at the old key would leave an entry reachable through a keying rule that no longer describes it.
- **Unsafe-method invalidation (#132):** after a successful unsafe request — any method except `GET`, `HEAD`, `OPTIONS`, `TRACE` and `CONNECT`, answered with a non-error 2xx/3xx status — Jul invalidates the effective request URI plus same-origin `Location` and `Content-Location` targets, removing both the `GET` and the `HEAD` key together with every `Vary` variant they own. Failed, timed-out, canceled and hijacked exchanges invalidate nothing. Cross-origin, opaque, non-HTTP and unparseable targets are skipped, so one origin can never evict another's entries.
- **Complete `Vary` variant membership (#132):** the pointer entry under a base key now records every variant key the resource owns, and membership is authoritative on lookup. This closes the case where deleting the base entry left hashed variant entries in the store that a rebuilt pointer could make reachable again. Membership is updated atomically with variant publication, persists across a disk-backed restart, and is capped at 64 variants per resource. A pointer entry written by an older Jul records no membership and therefore fails closed — one extra miss per `Vary` URL after upgrading, never a stale or unaccounted hit.
- **Conservative shared-cache rule for `Authorization` (#132):** a stored response may satisfy a request carrying `Authorization` only when it says `public`, `s-maxage` or `must-revalidate` (RFC 9111 §3.5). Publishing a response *generated for* an authenticated request is stricter still and requires `public` or `s-maxage`: `must-revalidate` says "do not serve me stale", not "this body is not user-specific". An unauthenticated stored response is never automatically reusable by an authenticated request, two requests carrying the same credential string do not thereby share a response, and `Vary: Authorization` is not a substitute for the permission. Credentials remain absent from cache keys, stored headers, logs, metric labels, tracing attributes and disk metadata.
- **`Range` and `If-Range` bypass the cache (decision D05, #132):** a request carrying either header now bypasses lookup and storage before any cache state is consulted. The origin's `206`, `200` or `416`, its `Content-Range`, its validators and its exact bytes reach the client untouched, the result is `X-Cache: BYPASS`, nothing partial is stored, and an existing complete representation is neither replaced nor evicted. Only the cache is bypassed: authentication, rate limiting, plugins, the WAF, tracing, metrics and the access log still run. Serving byte ranges from complete cached representations remains a documented future enhancement.
- **New `X-Cache: REVALIDATED` result value (#132):** reported when the origin confirmed the stored entry with a `304` during the request and the confirmed copy was served. It joins `HIT`, `MISS`, `STALE` and `BYPASS` as a `state` label value of `jul_cache_events_total` and is included in the Console hit-ratio denominator. The metric's **help string** still reads `(HIT/MISS/STALE/BYPASS)` because it is frozen by the v1.32.0 released metric contract; label values are not frozen by that contract, and re-wording is owned by #126/#134. No new metric family was added, and `jul_cache_revalidations_total` keeps its existing bounded outcome set for both background and synchronous validation.
- **Background revalidation now applies the foreground never-store rules (#132):** the in-memory revalidation recorder refuses `1xx` and `text/event-stream` responses instead of buffering them to `memory_max_size` before discarding them, so a background refresh cannot store or buffer a response the foreground path would have rejected.

- **Protocol-transparent response writers and upgrade handling (#133):** enabling `cache = true` on a route no longer changes what that route can do. A protocol-upgrade request (`Connection: Upgrade` plus a non-empty `Upgrade`, per RFC 9110 §7.8) now bypasses the cache before lookup and reaches the handler with the untouched response writer, so `httputil.ReverseProxy` can hijack the connection and complete the `101 Switching Protocols` handshake; previously the cache writer hid `Hijack` and a WebSocket upgrade over a cached route failed with 502. Both halves of the upgrade signal are required, so a stray client-supplied `Upgrade` header cannot disable caching for ordinary traffic. New `internal/respwriter` builds writer wrappers that expose **exactly** the optional interfaces the underlying writer implements — `http.Flusher`, `http.Hijacker`, `http.Pusher`, `io.ReaderFrom` — plus `Unwrap` for `http.ResponseController`; the cache, compression, metrics, access-log and tracing wrappers all use it, so an HTTP/2 or HTTP/3 stream is no longer falsely told it can be hijacked. `101`/`1xx` responses, anything written after a successful hijack, and `text/event-stream` bodies are never stored, and capture stops immediately so an open SSE connection accumulates nothing; a hijacked writer refuses further writes with `http.ErrHijacked`. Ordinary flushed (chunked) responses remain cacheable — the standard reverse proxy flushes every write of an unknown-length response, so treating a flush as "streaming" would have silently stopped caching most dynamic backends.
- **Generation-owned, cancellable cache revalidation and immutable cache entries (#131):** a `stale_while_revalidate` background refresh now acquires a generation lease before the originating request returns, so the handler generation it uses cannot retire — and close its gRPC connections, WASM plugin runtimes or static-file roots — while the refresh is still running. The refresh context is rooted in the process lifetime instead of `context.Background()`: it survives client disconnect, is cancelled by process shutdown and by forced generation retirement, and carries an absolute deadline of `[global] shutdown_timeout`. Only an explicit allow-list of request-context values is propagated (generation upstream snapshot, mutual-TLS client identity, request/trace ids); authentication claims, plugin invocation state, the client tracing span and client cancellation are deliberately not. Revalidation deduplication is keyed by cache key *and* handler generation, so a refresh on a retiring generation can neither be duplicated nor block a new generation, and every waiter is released and the call state removed on success, `304`, uncacheable, origin error, cancellation and panic alike. Published `Entry` values are now immutable: the `304` freshness refresh and the `stale_if_error` window extension clone and atomically replace the stored entry instead of mutating the shared object, removing a data race between concurrent readers and the revalidating writer. A cancelled refresh no longer extends the stale-if-error window. New bounded metric `jul_cache_revalidations_total{outcome}`. The new `internal/background` package is the small context seam between the server generation and the cache.
- **Atomic managed-apply terminal admission (#226):** terminal per-ID ledger visibility now occurs only after the coordinator has released the prior apply's config-mutation gate and the server reload-finalization gate. Managed history/audit/metrics/ledger side effects remain exactly-once and serialized through a dedicated finalization lock, eliminating scheduler-dependent false “previous apply is still in flight” rejections without permitting overlapping restoration or concurrent managed history writes.
- **Dedicated security-package gates (#129):** added independently enforced full-tag statement floors for RBAC, WAF, and WASM plugins; lean/full fail-closed negative matrices for missing build tags and invalid security policy; a deterministic checker that fails on malformed or missing package coverage; exact baseline/floor documentation; and a reproducible `make security-gates` local command. These focused gates supplement rather than replace the repository-wide coverage, race, fuzz, vulnerability, CodeQL, E2E, and soak evidence.
- **Explicit access-log enablement (#124):** `[observability.access_log].enabled` now distinguishes the default-on state from an explicit disabled state. `enabled = false` opens no access-log file/syslog resources and emits no request records to stdout or the Console access tail while process, security, audit, health, metrics, and tracing remain independent. Enabled blocks reject an explicit empty sink list; dormant sink settings remain validated. Legacy global/per-server log-destination fields are now linted and classified as `ignored_deprecated`, never as pending restart. The Traffic Controls Console includes a guided restart-aware editor.

### Added
- **The eleven resilience scenarios are validated, with deterministic test-only fault injection (#144):** connect refusal, slow response, mid-body failure and backend disappearance are injectable from the test binary and **only** from the test binary — a production knob that makes a backend stall or truncate mid-body is a way to degrade a proxy from the configuration file, which is a worse problem than the one it would help diagnose, so keeping it in `_test.go` makes that structural rather than a promise. Scenario 1 pins the correction that reads like a bug: with every backend down the request **is** admitted and released, because admission is capacity and is evaluated before eligibility, so the pending queue never fills during a total outage and the reason is `upstream_connect_failed`, never `proxy_overloaded`. Scenario 3 is the only one where `proxy_overloaded` is correct. The half-open scenario distinguishes a circuit that answered (`upstream_unavailable`, no dial) from a probe that was actually sent (`upstream_connect_failed`), which is the difference between a backend that can recover and one that cannot. The mid-body test asserts that six clients produce exactly six upstream requests; it was verified against a failure that happens *before* any byte is written, which produces nine, so the retry machinery is demonstrably live and the suppression is demonstrably real.
- **Retry amplification is measured, not asserted (#144):** `TestAmplificationUnderTotalOutage` drives 100,000 requests at a pool where every backend refuses and counts every upstream attempt in the retry adapter — the only place that sees all of them, including the ones the budget denied. Measured: **1.10003×** at `retry_budget_percent = 10`, against **3.00×** for the same outage with no budget, so the budget's effect is a measured difference rather than a number in isolation. This also settles the acceptance criterion, which asks for ≤ 1.1×: that bound **is not achievable by this design at any volume**, because `Allow` grants while `retries < floor(primaries * percent / 100) + minFreeRetries` and the free-retry floor is added unconditionally. The 100,000-request run is over by exactly three requests — the floor — not by a proportion. The floor is deliberate (without it a pool with almost no traffic could not fail over at all, which is when a stale connection is most likely) and is an absolute constant rather than a multiplier: at most 3 extra requests per 10-second window whatever the inbound rate, so it cannot produce amplification collapse. The test asserts that the overshoot stays an absolute handful and does **not** grow with load, which is the property that matters. Recorded in `docs/soak-evidence.md`; the criterion should be read as ≤ 1.1× + 3 requests per window, or amended.

- **`upstream_set_resilience` typed patch operation (#144):** the whole `[upstreams.resilience]` block, editable through the same reviewed preview/diff/apply path as every other structured change, gated by the `config:write` that already covers patch operations — no new RBAC scope, because resilience is not a security boundary. It replaces the block rather than merging into it, matching `upstream_set_health_check`: a partial merge would make the result depend on state the caller cannot see in the request they are sending. Bounds are checked by calling the runtime's own `resilience.Resolve` rather than restating the ceilings where the two could drift, so a value the configuration file would reject cannot be smuggled in through a patch. Because `max_fails` and `fail_timeout` still have a deprecated upstream-level spelling and a configuration carrying both is rejected, setting either through this operation *moves* them out of the old position — reported in the operation summary rather than done silently, since the alternative is an operation that produces a configuration which cannot be loaded.
- **Resilience changes are diffed field by field (#144):** left to the registry completeness pass, changing four limits produced a row for *every* resilience path whether or not it changed, each with empty before/after values and the schema path (`upstreams.*.resilience.max_fails`) as the name — thirteen rows that told an operator nothing about what they were about to apply. `diffResilienceFields` now reports only what changed, named by pool, with real before and after values. An explicit `circuit_half_open_probes = 0` renders as `0 (unbounded)` against `(default)` and carries a warning, because it asks for exactly the behaviour the circuit breaker was introduced to remove.

- **`GET /api/upstreams/{name}/resilience` (#144):** the per-pool runtime view — limits actually in force and which configuration key supplied each, live active/pending/connection counts, the retry budget with its remaining allowance, and per backend the consecutive-failure count, the cooldown deadline and the half-open probes left. This is the surface the per-backend metric label was withdrawn in favour of: an address costs one field in a response queried on demand, where the same address as a Prometheus label cost a time series per pod for the life of the process. One entry per scheme, since a name can serve both an http and an https pool. An unknown pool is a 404 and a pool with every backend down is a 200 with `verdict: "down"` — deliberately different answers, because a pool that has vanished and a pool that is failing call for opposite responses. `status:read` gates it; no new scope. The verdict is produced by the same classifier `/api/apps` uses, and a table test drives every pair of backend states through both to pin that the two endpoints can never disagree. `Budget.Status` reports the allowance without consuming it — a diagnostic that spent what it reported would deny a real retry every time an operator refreshed the page — and a test asserts the reported remaining equals what `Allow` actually grants.

- **Ten bounded resilience metrics (#144):** admission (`jul_upstream_active_requests`, `jul_upstream_pending_requests`, `jul_upstream_connections`), selection (`jul_upstream_backends_eligible`, `jul_upstream_circuit_state`), retry (`jul_upstream_retry_attempts_total`, `jul_upstream_retry_budget_denied_total`), refusal (`jul_upstream_admission_rejected_total`), transitions (`jul_upstream_circuit_transitions_total`) and generation retirement (`jul_transport_retired_total`). Every label is a configured pool name or a closed enum, and **no metric carries a `backend` label** — per-backend circuit detail is a count per state, not a series per address, which is the defect this programme removed. The rejection and transition label sets are asserted *equal* to the reason enum and the backend-state set, not merely contained in them: a value outside the enum would be unbounded cardinality, and an enum member never exported would be a condition an operator cannot alert on.
- **The five live gauges are read at scrape time, not pushed (#144):** admission is the hottest code in the proxy, and a gauge write per admit and per release would cost every request to maintain a number nobody reads between scrapes. A scrape-time collector is also self-correcting — a pushed gauge that misses one decrement stays wrong until restart — and a retired pool simply stops being reported, with no series to delete. `jul_upstream_connections` is sourced from Jul's own dialer because `net/http` enforces `MaxConnsPerHost` internally and exposes no live count; the wrapper's release is idempotent, since a transport may close a connection more than once and a negative connection count would be worse than none.
- **`upstream.admission` span, retry attributes, and an `upstream_reason` access-log field (#144):** a request parked in the pending queue was previously a gap in the trace with nothing accounting for it, and a backoff was unattributed latency. Each attempt span now carries `retry.attempt` and, from the second attempt on, `retry.backoff_ms`, so a trace shows which wait preceded which try rather than one total that explains nothing. Both are numeric attributes — a number recorded as a string cannot be filtered or aggregated by a tracing backend, which is the only reason to record it, so the seam gained `SetInt`. The backoff is computed by the retry driver but belongs on the caller's span, so the driver reports it through a hook rather than the handler guessing.
- The access log's `upstream_reason` is a **format-contract addition**, recorded in `docs/compatibility.md`: a consumer that rejects unknown fields needs updating. The value comes from the closed taxonomy, and because `internal/middleware` takes it as a plain string to keep the dependency pointing one way, a test in `internal/handler` — the lowest package that can see both — asserts the logged set equals the enum exactly.
- Documented that `jul_http_requests_in_flight` and `jul_upstream_active_requests{pool}` legitimately differ: the first counts inbound requests, the second admitted upstream work, so static files, cache hits, redirects and blocked requests appear in one and not the other. The first operator to compare them would otherwise file a bug.

- **A closed upstream failure taxonomy (#144):** eleven reasons in `internal/upstream` — the lowest package every consumer already depends on, so `internal/handler`, `internal/transcode`, `internal/stream`, `internal/auth`, `internal/admin` and `internal/observability` all import downward rather than `internal/stream` having to import `internal/handler`. The client-facing status and the operator-facing reason are deliberately different resolutions of the same event: `upstream_unavailable`, `circuit_open`, `proxy_overloaded` and `backend_at_capacity` are all 503 to a client and are never merged for an operator, because "the backends are gone" and "Jul is deliberately not calling them" call for opposite responses. Overload is 503 rather than 429 — 429 blames the client for a condition that is not theirs, and is already the rate limiter's status — and therefore `UNAVAILABLE` rather than `RESOURCE_EXHAUSTED` on gRPC, since `RESOURCE_EXHAUSTED` maps back to 429 and would contradict the HTTP path. Retry suppression keeps the last attempt's own status, so a spent budget cannot hide a 500 the client needs to see. gRPC codes are stored as numbers to keep the package stdlib-only, with a `grpc`-tagged test asserting each against the `codes` package.

- **Backend state follows the workload, not the address (#295):** a backend's in-flight count, failure history and health verdict were keyed by address alone, and an address is not an identity. Kubernetes recycles pod IPs within seconds, so a replacement pod inherited the failure history of the one it replaced and arrived partway to being taken out of rotation — for failures it never caused. Discovery now carries the provider's own identity: the pod UID from `targetRef.uid` on the `EndpointSlice` endpoint, which `k8sEndpoint` did not parse at all, and Consul's `Service.ID`. DNS, DNS SRV and static servers have none to offer and are unchanged, keeping the address as the reuse key because there is nothing else to go on.
  The identity **narrows** the address rather than replacing it, which is a deliberate limit: a workload that moves address still gets a fresh backend, because `Backend.Address` is read without a lock by the dial path and rewriting it in place would be a data race for the sake of a case — a pod keeping its UID across an IP change — that costs only the state it had accumulated at the address it left. The **dial** identity stays address-based and untouched, because it answers a different question: two workloads at one address are still one place to connect, and retry exclusion within a request must not re-try an address it already tried just because the pod behind it changed mid-request.
  Discovery no longer launders its results through the public server config on the way to the pool. `Pool.UpdateTargets` takes the resolved targets directly, so an identity does not have to become a TOML field to reach the code that needs it — a pod UID is not something an operator writes in a configuration file.
  **Behaviour change:** a Consul service that re-registers with a different `ServiceID` now resets its state, which is the intended semantic for a logically replaced workload.
  The gRPC transcoding connection cache is re-keyed from a bare address to the dial identity and carries the workload identity alongside it, so a replacement pod at a recycled address gets a fresh connection instead of one established to its predecessor. The old connection is **retired rather than closed**, because a stream started against the previous workload may still be draining; the reconciler stays level-triggered, so the worst-case lag between a backend leaving and its connection closing is 60 seconds, now documented.
- **Forward-auth and JWKS gain transport resilience, and fail closed (#293):** both dependencies sit on the request path of every authenticated request, so an unbounded number of subrequests to a struggling auth service is the same amplification this programme bounds everywhere else. `forward_auth.url` and `jwt.jwks_url` now resolve through the shared upstream primitives — a host naming a configured `[[upstreams]]` is load-balanced across replicas, anything else becomes a pool of one — which brings both under the same admission, passive health and retry accounting. `timeout` replaces what was a hardcoded ten seconds in two places; leaving it unset keeps exactly that value.
  **Every failure denies.** An admission rejection, a spent retry budget, a pool with no available backend and — when the breaker lands — an open circuit all deny with `503`; a request is never allowed through unauthenticated because a resilience control fired. That is asserted by test rather than assumed, because "fail open on dependency failure" is a defensible-sounding default in other systems and a critical vulnerability here. The shape carries it: every one of those conditions reaches the caller as an error and the caller denies on error, so the property follows from the structure instead of from a rule each call site must remember. Deliberately verified by breaking it — forcing the error branch open makes both fail-closed tests fail, and the request is *still* denied, because a zero-valued decision is not an allow.
  **The scope is transport only, and that is a decision rather than an omission.** An HTTP response is an answer whatever its status, so an auth service returning `500` forever neither fails over nor removes a healthy replica from rotation, and a `401`/`403` reaches the client unchanged — all pinned by tests that count calls and check backend availability, not just status codes. The two dependencies do not even agree on what failure means: JWKS treats any non-`200` as a refresh failure while forward-auth treats a non-2xx as a legitimate application result, since `401` and `403` *are* the answer. Making `5xx` or `429` trip a breaker needs a generic outcome-classification seam — the same seam `retry_on` needs — so it is one deferred extension with two consumers, not an auth-specific second breaker.
- **Transcoded unary gRPC calls are retried; streaming still is not (#292):** the asymmetry is the point rather than an omission. A unary call's request is an in-memory `dynamicpb.Message`, so replaying it costs nothing and cannot fail, and its response is fully decoded before a byte is written — the whole call sits inside the retry boundary. A streaming call has already written framing by the time it can fail, and replaying it would deliver a second stream into a client consuming the first; native gRPC passthrough is opaque HTTP/2, where Jul cannot frame messages or even tell unary from streaming. Both stay unretried, and a test pins that a dead backend at the head of the pool ends a streaming request where the unary path would have failed over.
  The idempotency gate reads **both** available signals: the HTTP binding (`GET`/`HEAD`/`OPTIONS`/`TRACE`/`PUT`/`DELETE`) **or** the method's own `idempotency_level` of `NO_SIDE_EFFECTS` or `IDEMPOTENT`. The annotation is consulted because the binding alone is too coarse — a method mapped to `POST` purely because it takes a request body may still be declared side-effect-free, and ignoring that would discard an explicit statement by the API's author. **`IDEMPOTENCY_UNKNOWN` is never retried**, because silence is not a promise and the method most likely to be silent about it is the one that charges a card. Only `UNAVAILABLE` and a failure to establish the connection are retried; every other code is the application's answer, and asking a second backend the same question returns the same answer more expensively while doubling load on a service already saying no. The failed backend is excluded from re-selection, and a connection-establishment failure keeps its own `502` rather than decoding an absent response into some status code.
  The override-merge rule and the retry-safe method list move to `internal/upstream` as `Pool.RetryRequestFor` and `RetrySafeMethod`, so the HTTP proxy, the CGI adapters and the transcoder share one definition. A method list that drifted between adapters would mean a request retried on one route and not on another for no reason anybody could state — and the transcoder cannot import the handler package, so without a shared home the list would have been duplicated by construction.
- **FastCGI and uWSGI become retry adapters (#291):** both now answer to the shared decision function from #290 rather than to protocol-local rules, so an FPM or uWSGI instance that is down costs one failed dial instead of the request — which is what making them pool members in #285 was for.
  Reaching the retry boundary meant replacing `gofast.NewHandler`. That handler hardcodes `502` for a dial failure and `500` for a session failure and reports both with `log.Printf` to the **global** logger, ignoring its own `SetLogger` on exactly those paths, so a FastCGI backend problem bypassed Jul's status mapping, its bounded reason taxonomy, its structured logger and its per-pool log throttle all at once. Jul now drives gofast's three exported steps itself — `newClient`, `sessionHandler`, `WriteTo` — with the retry loop around the first two, which is also the only way the boundary becomes expressible: `WriteTo` is the moment a byte can reach the client. **No vendored changes.** uWSGI's send side is factored into one step for the same reason, so its boundary is everything before `writeCGIResponse`.
  One correctness trap is worth recording, because it would have shipped as silence rather than as a failure. The HTTP path tests replayability with `Body == nil || GetBody != nil`, which is right for the outbound request `httputil.ReverseProxy` builds — it nils the body when there is none — and **silently wrong for a server request**, where `Body` is always non-nil and merely returns EOF immediately. Copied verbatim into the CGI adapters it reports "not replayable" for every request and disables retry entirely, while looking correct in review and passing every test that does not count attempts. `replayableBody` now recognises a body-less request explicitly.
  The other half of that is a deliberate limit rather than a gap: `net/http` never sets `GetBody` on a server request, so a CGI request that really carries a body is attempted once even with a retry-safe method. Buffering it to make it replayable is precisely the unbounded-memory failure this programme exists to prevent. Both halves are pinned by test — the rewind path with an explicit `GetBody`, and the production behaviour without one.
  Passive health and the dial-failure log throttle now apply per attempt on both adapters, so a backend outage cannot be noisier or quieter through the CGI path than through the HTTP one, and the FastCGI application's stderr stream is reported through the structured logger with the request id instead of `log.Printf`.
  The retry boundary turned out to fall slightly earlier than it first appears. A FastCGI backend that accepts the connection and closes it without answering does **not** fail the session step — the write is buffered, so the failure is only observable while reading the response, and `WriteTo` reads from the backend and writes to the client in the same step. Retrying there would require buffering the whole response first, which is the memory failure this programme exists to prevent, so it is not retried and a test pins that rather than leaving the next reader to rediscover it.
- **Retry gains a deadline, bounded backoff and a budget (#290):** `balancingTransport.RoundTrip` retried with **no backoff, no overall deadline and no budget**, and with `proxy_retries` unset it tries every distinct backend once — so a *total* outage multiplied upstream load by the backend count, at the moment the upstream could least afford it. Five keys bound it: `retry_attempts`, `retry_deadline`, `retry_backoff_initial`, `retry_backoff_max` and `retry_budget_percent`. Every default reproduces today's behaviour exactly.
  The eligibility rule is now **one pure function** rather than a condition scattered through a transport, so the CGI adapters and the transcoder can answer to it without re-deriving it, and it is table-tested exhaustively — including the **precedence** between conditions, because a rule that returns the right yes/no with the wrong reason sends an operator to tune a control that was never involved. A response whose first byte has been delivered can never be retried whatever the budget says, and reporting "budget exhausted" for it would be a lie with a plausible fix attached.
  **The deadline dominates the sequence, not the attempt**: the effective bound is `min(request deadline, start + retry_deadline)` and every attempt and every backoff sleep runs under it, so three attempts against a three-second deadline take three seconds rather than nine. Backoff doubles with **full jitter**, drawn uniformly from `[0, interval)` — half-jitter would halve the spread for no benefit, and spread is the whole point, since every client of a backend that just died otherwise computes the same interval and returns together. When the clamp leaves no room to sleep *and* attempt, the loop stops rather than sleeping: waking at the deadline only converts a failure into a slower one.
  **`retry_budget_percent` is what actually bounds amplification.** `retry_attempts` caps one request and does nothing about a thousand requests retrying at once, which is the case that takes an upstream down. Over a trailing window retries are permitted while `retries < floor(primaries * p / 100) + 3`, claimed by CAS so the bound is exact under concurrency — pinned by a test that would catch a read-then-increment race the race detector cannot see, because it is a lost update rather than a data race. That bounds upstream load at `(1 + p/100)×`, so 1.1× at `p = 10` against up to 3× for an unbudgeted `retry_attempts = 3`. The free floor of three exists so a nearly idle pool can still fail over, which is exactly when a stale pooled connection is most likely. The window counters live on the pool and a policy swap changes only the percentage: **a reload does not refill the budget**, because a reload during an incident is the least appropriate moment to forgive the retry load that helped cause it. Two locations sharing a pool share one window, which is correct — the budget protects the backend, not the route — and documented because it is surprising.
  Two regressions are pinned because violating them is a correctness failure rather than a performance one: **no retry after a response byte has been delivered**, and **no TLS downgrade on failover** — a backend whose scheme does not match an `https` route is refused before being dialled, and the refusal is terminal, since retrying into the next plaintext backend would be the same downgrade one hop later. A fuzz target over window rotation with arbitrary forward *and backward* clock jumps asserts the real contract, that every granted retry satisfied the bound at the moment it was granted; 3.5 million executions found no violation. Along the way it established a property worth stating rather than hiding: a retry is recorded in the bucket it was granted in while the primaries justifying it may span both, so when the older bucket ages out the stored ratio can briefly read above the limit. Nothing is over-spent and the effect is self-correcting; ageing retries out with the traffic that earned them would need a timestamp per retry and would make the hot path allocate. `BenchmarkRetryBudgetAllow` is **0 allocs/op** at 44 ns, and the decision function 0 allocs at 7.5 ns.
  **`proxy_retries` is deprecated, not removed.** It is a live, consumed public field and Jul rejects unknown TOML fields strictly, so deleting the spelling would turn working configurations into startup *and reload* failures. `retry_attempts` becomes the canonical name at both scopes so the override rule reads as one word overriding the same word; setting both on one location is a validation error rather than a silent precedence nobody can read off the file. The four stateless retry keys are location-overridable with a zero inheriting rather than meaning "unlimited" — the rule `max_connections_per_backend` already follows — while `retry_budget_percent` owns a window and stays pool-scoped, enforced by the type rather than by a validation rule that could drift from it. Implements the first slice of [#142](https://github.com/victornife/jul/issues/142).
- **Upstream resilience, as one capability (#141, closing work in #287):** the four slices that follow compose into a single property — **the amount of concurrent work Jul will hand a backend is bounded, and the bound is the same object no matter which protocol asked for it.** HTTP/1.1, HTTP/2, HTTP/3, WebSocket upgrades, server-sent events, native gRPC, gRPC transcoding, FastCGI, uWSGI and L4 TCP all acquire from one per-pool admission counter and hold it for their whole unit of work; UDP is bounded per listener by `max_udp_sessions` instead, because it has no client to park and no way to signal a rejection. [docs/upstreams.md](docs/upstreams.md#the-accounting-model-in-one-place) now states the five quantities — pool-active, per-backend-active, pending, physical connections, UDP sessions — in one table, together with why `jul_http_requests_in_flight` and `jul_upstream_active_requests` legitimately disagree: the first counts inbound requests including cache hits and rejections, the second only the subset admitted to a backend, so a deployment that forced them to match would be lying about one of them.
  The sizing guidance is measured rather than asserted. `max_pending_requests` is the number most likely to be set wrongly, because admission is innermost: a parked request already holds a parsed `*http.Request`, its header maps and any auth or WAF context, so the waiter structure is a rounding error beside it. Measured at **~7.5 KB of live heap per parked request** (200 parked → ~1.5 MB), which is two orders of magnitude above what the waiter struct alone would suggest. `max_active_per_backend × backend_count` must reach `max_active_requests` or the pool limit is unreachable; `jul lint` warns for static server lists and necessarily cannot under discovery, where the metric is the authority.
  Evidence at this SHA: a cross-protocol churn test that drives all four handler families against concurrent policy swaps and is clean under `-race`, with counters at zero and goroutine count flat at quiesce; a fuzz target over acquire/release/cancel/reload/backend-update interleavings (**70 007 executions, zero invariant violations**) asserting `0 ≤ Q_p ≤ max_pending`, `A_p ≥ 0` and `Σ A_b ≤ A_p`; a 256-deep saturated queue that adds no goroutines; and `BenchmarkProxyRoundTrip`, which did not previously exist, showing **no significant change** against the pre-programme baseline (58.1µs vs 63.3µs serial, p=0.315, n=10; 32.09µs vs 31.78µs parallel, p=0.383, n=20) at a cost of exactly two allocations per request for the release closure. `BenchmarkAdmit_*` answers the open question of whether the counter needs sharding with data rather than intuition: 23–28 ns uncontended and 155 ns at `GOMAXPROCS=16` fully contended, which is ~0.27% of a ~57µs request path — **sharding is not justified**, and the benchmark is committed so the answer can be rechecked when the ratio changes.
  **The 24-hour soak remains outstanding.** `burn-in-resilience.toml` ships with the load commands and falsifiable pass criteria, and [docs/soak-evidence.md](docs/soak-evidence.md) records the run as **not performed** rather than implying coverage that does not exist.
- **L4 TCP admission and a stream-owned upstream registry (#286):** TCP stream routes were unbounded — `handleTCP` counted connections for metrics and nothing more, and no TCP concurrency limit existed anywhere in the repository. `[upstreams.resilience] max_active_requests` now bounds them, meaning **concurrent connections**, because at layer 4 the connection is the unit of work; a connection over the limit is closed without a response, since a raw socket has no status code to send, and the rejection is counted under a bounded `overloaded` reason. **UDP is deliberately untouched.** `max_udp_sessions` already bounds it per listener with LRU eviction of an idle victim, which is the protocol-appropriate answer where there is no client to park and no way to signal a rejection, so setting `max_active_requests` on an upstream reached by a UDP route is now a **validation error** rather than a second, disagreeing admission mechanism. The resulting asymmetry — UDP capped per listener, TCP per pool — is documented rather than left to be discovered. `stream.Server` now owns its own `upstream.Registry` instance: the HTTP one is a single global staging transaction driven by the handler factory under one mutex, while stream reload is a separate fan-in, so sharing it would have meant restructuring the apply transaction for no gain in fidelity — an upstream referenced by both an HTTP location and a stream route already had two independent pools. That closes a real gap: stream pools were rebuilt on **every** stream reload, so an L4 backend lost its in-flight accounting each time the configuration was touched for any reason. Preflight validation stages into a transaction it always aborts, so checking a candidate configuration cannot disturb a live pool.
- **FastCGI and uWSGI become upstream pool members (#285):** they were the least protected path in Jul's entire data plane. `newFastCGIHandler` built `gofast.NewClientPool(factory, 0, ...)` and `uwsgiHandler` dialled per request, so concurrent backend connections were unbounded, with no load balancing, no health checking and no failure accounting — while PHP-FPM's fixed `pm.max_children` makes bounding concurrency *more* valuable there than for a typical HTTP backend, since admitting past it only builds a queue inside the application server where Jul cannot see it. `fastcgi_pass` and `uwsgi_pass` now accept a named upstream or a literal socket and resolve through the registry exactly as `proxy_pass` does, so both gain admission, balancing, active health and passive failure accounting. `Backend` and `BackendIdentity` carry a `Network` (`tcp` or `unix`) derived from the address form by one shared parser, `[[upstreams]] servers` accept `unix:` addresses, and TCP probes dial the backend's own network — so an FPM pool of unix sockets is a first-class upstream. An `http` health check against a unix-socket backend is a validation error rather than a probe that can never succeed, because there is no host to put in a URL. `uwsgi_pass` honours the location's `proxy_connect_timeout` instead of a hardcoded ten seconds.
- **Backend connection bounds, and admission for native gRPC and transcoding (#284):** `max_connections_per_backend` bounds physical sockets to one backend host, mapping to Go's `MaxConnsPerHost` — the only lever that limits sockets without defeating connection pooling and that honours the request context while a request waits for a dial. It is stateless, because a transport is already built per route, so it may be set on `[upstreams.resilience]` or on `[servers.locations.resilience]`, with the location winning; a location value of `0` inherits rather than meaning "unlimited", because every other zero in this configuration means "not set" and one field reading its zero the other way would be a trap. Two exemptions are deliberate. It does **not** apply to native gRPC or gRPC transcoding, where one HTTP/2 connection carries every stream and a socket bound would therefore bound nothing — `jul lint` warns when it is set on such a route, because silence would leave an operator believing a limit is in force. And **health-check clients are exempt**: probes are built on their own client, so a pool whose sockets are all busy serving traffic can still dial a probe and notice a backend recovering, where a shared bound would leave a saturated pool unable to observe its way out. Native gRPC passthrough and gRPC-JSON transcoding now acquire pool admission, which they could not before: `NewGRPCProxy` returned a bare `*httputil.ReverseProxy`, so both are wrapped in one shared handler that admits before the call and releases when it returns. That duration is the honest one — for a server, client or bidirectional stream it is the stream's whole lifetime, so a gRPC stream open for hours counts as one busy request for all of it, and an overloaded gRPC route answers `UNAVAILABLE` (via HTTP 503) rather than `RESOURCE_EXHAUSTED`, which maps back to 429 and would contradict the HTTP path. Closing a retired generation now also drops the gRPC transport's idle HTTP/2 connections, which nothing previously did. The accounting matrix is documented and asserted per protocol: HTTP/1.1 with and without keep-alive, concurrent HTTP/2 streams, real QUIC streams over one HTTP/3 connection, WebSocket for the full upgraded-connection lifetime, server-sent events, gRPC unary and streaming, and transcoding. One property that looks like a leak and is not is pinned by test: an upgraded connection ends when **both** directions end, so a backend closing its half while the client's half is still open does not release the slot — the tunnel is still open. `max_connections_per_backend` is `hot_reload`, because transports are already rebuilt with the generation that owns them.
- **Upstream admission and overload control, `[upstreams.resilience]` (#283):** Jul accepted every request that reached a proxy route and pushed it at a backend, so an overloaded upstream absorbed unbounded concurrency and the operator's only lever was an inbound rate limit that cannot know what a backend can take. Four pool-scoped keys now bound it: `max_active_requests` (admitted logical requests, streams and connections), `max_active_per_backend`, `max_pending_requests` and `pending_timeout`. **Every default is zero and every zero reproduces the previous behaviour**, so an upstream without the block is unchanged — with one deliberate asymmetry: `max_pending_requests = 0` means *no queue*, not an unlimited one, because an unbounded pending queue is the out-of-memory failure the control exists to prevent and it must not be expressible. The primitive is counters plus limits rather than a rebuilt one: a CAS fast path that takes no lock below the limit, and above it a bounded FIFO in which the parked goroutine is the inbound `net/http` goroutine that already exists, so a full queue costs no goroutines of its own — a counting channel cannot be resized on reload, `x/sync/semaphore` cannot bound its waiter list, and `sync.Cond` cannot honour request cancellation, so none of the three could implement it. Releasing a slot hands it directly to the head of the queue instead of decrementing, which is what makes the queue strictly first-in-first-out, stops a late arrival barging past a request that is already waiting, and makes recovery after a limit decrease monotonic. `max_active_per_backend` is applied as a **selection filter** and never as a second queue: a saturated backend is simply not a candidate, because queueing inside backend selection would block one backend's traffic behind another's, and a request holding a pool slot while it waits for a backend slot is a deadlock. Rejection is `503` with `Retry-After` and never `429` — `429` says the *client* sent too many requests, and a saturated pool is not the client's fault. Admission sits innermost, immediately around the upstream call, so a cache hit or a WAF-blocked request never consumes a slot while background cache revalidation correctly does; the cost is that under sustained overload Jul still pays full WAF and authentication work for requests it then rejects, which is accepted because counting exactly the work that reaches a backend is worth more than saving CPU on the rejection path. All four keys are `hot_reload`: the resolved policy is swapped into the live pool as an atomic pointer and the pool is deliberately **not** rebuilt, since rebuilding would discard the very counters the limits govern — so a lowered limit never evicts requests already in flight, the overshoot only ever shrinks, and a raised limit wakes queued requests at once. `pending_timeout` may not exceed `global.shutdown_timeout`, and a forcibly retired handler generation wakes its own queued requests with a `503` rather than letting them be admitted onto a transport that is about to close. The controls are stateful, so they are pool-scoped only and a `[servers.locations.resilience]` block is rejected rather than silently ignored; a literal `proxy_pass` target still builds an unregistered pool of one, so its counters reset on reload, which is now documented as a reason to name an upstream. `jul lint` warns when `max_active_per_backend` multiplied by the backend count cannot reach `max_active_requests` (the pool limit is then unreachable while the pending queue sits empty) and when a queue is configured with no timeout. Implements the first slice of [ADR 0017](docs/adr/0017-upstream-resilience-and-overload-control.md).
- **Bounded observability for backend dial failures, stream and HTTP alike (#275):** a dial failure was logged once per connection/request with no throttle and no counter — a log-amplification vector during an ordinary backend outage, no attacker required, called out but deliberately left unfixed alongside the route-miss/PROXY-protocol throttling in #136 because throttling it without a counter would have traded the flood for a blind spot. `jul_stream_backend_dial_failures_total{proto,reason}` (TCP/UDP) and `jul_http_backend_dial_failures_total{reason}` (reverse proxy) now count every failure — `reason` is the bounded set `timeout`/`refused`/`no_backend`/`other` — regardless of whether the accompanying line is emitted. The log itself is bounded without losing the signal: `Pool.MarkFailure`/`MarkSuccess` now report whether a call actually tripped or cleared a backend's passive-health cooldown, so that rare transition is logged unconditionally (`stream: backend marked down` / `recovered`, `proxy backend marked down` / `recovered`) while failures against an already-known-down backend are a 10-second throttled heartbeat per pool, reusing the same throttle for the stream dial site and the HTTP `RoundTrip`/`ErrorHandler` sites so a backend outage cannot be quieter on one transport than the other. The transition hook is shared with the active health checker's `HealthHook` (wired once by the registry, independent of whether `health_check` is configured), so a passive, dial-triggered trip now reaches the same gauge and Console Upstream Health History entry an active probe failure already did — closing the passive-health logging gap noted in ADR 0017. Client-cancelled requests and backend-TLS-identity failures (already handled via `tls_failure`) are excluded from the new counter and throttle. The Console Status overview gains a "Backend dial-failure accounting" row under Observability; it stays config-driven (no live counter value), consistent with that panel's existing contract.

 conveying a verified client certificate to a backend was possible only through operator-named headers carrying `$ssl_client_*` variables, and Jul overwrote *the headers the operator happened to list*. Anything not listed — an `X-Client-DN` the backend trusted but the `headers` block did not mention — flowed through from the client untouched. Address identity has never had that gap, because `X-Forwarded-*` is cleared and rebuilt on every proxied request regardless of configuration; certificate identity now works the same way. `Client-Cert`, `Client-Cert-Chain` and the pre-standard `X-Forwarded-Client-Cert` are stripped from **every** proxied request, including ones where no client certificate was negotiated, as RFC 9440 §2.4 requires. `[servers.tls.client_auth] forward_certificate = "leaf"` (or `"chain"`) then emits Jul's own assertion in the standard encoding. The standard is preferred over the NGINX variables because it declined exactly the design they represent — it carries the whole certificate rather than cherry-picking fields, having observed that per-deployment field names make independent implementations "cumbersome or even impossible" to interoperate; `$ssl_client_*` remains as the migration path. The DER is retained on the request only when a listener asks for forwarding. One limit is stated rather than implied: Jul cannot sanitize an arbitrary operator-chosen header name, because it cannot know a backend trusts it.

- **PROXY protocol on HTTP listeners (#136):** a TCP load balancer that preserves the client with the PROXY protocol rather than a forwarding header — AWS NLB, GCP TCP LB, HAProxy in TCP mode — had no expression in the configuration, so those deployments simply lost the client address. `proxy_protocol = "in"` on a `[[servers]]` block strips the header ahead of the TLS wrap and makes the advertised address the listener's transport peer, so every consumer above it behaves as for a direct connection, and a CDN in front of the balancer still composes on top through `X-Forwarded-For`. `client_address.trusted_proxies` is required and names the balancers permitted to assert an address; a connection from outside the set is refused rather than served on its own address. Enabling it together with HTTP/3 on one listener is a validation error: QUIC negotiates TLS inside the transport and carries no plaintext framing, and a listener must not derive the client address two different ways depending on the protocol a client negotiated. The parser moved to `internal/proxyproto` so the L4 and HTTP boundaries share one implementation.

### Security
- **Service discovery authenticates the registry it trusts (#136):** discovery providers pass Boundary C, which authorises the *destination*, and nothing authenticated the *peer* — yet the safety of backend selection rests on them, because a poisoned answer is only harmless if the address it supplies came from the intended authority. Consul was reachable over plaintext HTTP only, so its ACL token crossed the network in the clear and was replayable by anything on the path; a new `[upstreams.discovery.consul.tls]` block resolves the same `backend_tls` policy type, so a control-plane peer is authenticated by the same proof as a data-plane one and `jul lint` warns when a token still rides plaintext. The Kubernetes `insecure_skip_tls_verify` escape hatch had none of the treatment its `backend_tls` equivalent gets; both now produce a `SeverityError` lint finding (so `jul lint` exits 1 without `-strict`), one startup warning per affected upstream, and a bounded `discovery_insecure` count in the Console security projection that carries no provider or upstream name.

- **An inbound L4 PROXY header now requires a declared trusted proxy (#136):** `[[stream]]` parsed a PROXY v1/v2 header from *any* peer whenever `proxy_protocol` was `in` or `both`, took the advertised address as the client, and re-emitted it to the backend with `out`. A PROXY header is an assertion, not a kernel fact, so anyone able to reach the listener could choose the source address the backend saw — and L4 backends are exactly the ones that authorise by source address (`pg_hba.conf`, Redis, MySQL host grants). The new `trusted_proxies` field is **required** whenever a header is ingested and rejected when none is, using the same parser and canonical-prefix rule as `[servers.client_address]`. A connection from outside the set is **refused** rather than degraded to its own socket address: an `in` listener declares that all traffic arrives via the proxy, so degrading would let a direct client bypass the requirement by sending no header at all. This is the one place the L4 boundary deliberately differs from the HTTP one, which falls back to the peer because an HTTP listener legitimately serves proxied and direct traffic side by side. Existing configurations are unaffected unless they ingest a header — `out`-only emission needs no trust set.

- **A degraded client identity no longer satisfies a CIDR rule (#136):** when a *trusted* proxy asserts a chain Jul cannot use — malformed, oversized past 8 KiB, or longer than `max_hops` — derivation falls back to the direct peer. That fallback is right for serving and logging, but the peer is the proxy, and CIDR authentication was judging it as if it were a client. Because the trusted-proxy range and an internal allow list are usually the same network, an attacker behind the proxy could pad `X-Forwarded-For` past a bound and be admitted to a range their real address is not in; the mirror case let them evade a deny rule aimed at their own address. Both are decided purely by attacker-supplied header bytes. `Identity.Attributed()` now distinguishes an address that names a client from one that names an unresolved hop, and the CIDR gate fails closed on the latter instead of evaluating either list against a proxy address. An untrusted peer stays attributed — it asserted a header Jul ignored, and it really is the client — so direct traffic is unaffected. Proven by `TestCIDRAuthUsesCanonicalClient`, whose new cases return `200` before the fix and `403` after.

- **Remote peers can no longer set the log volume of an L4 listener (#136):** three `[[stream]]` diagnostics fired once per connection on conditions the connecting peer chooses — a refused PROXY-protocol connection, a rejected PROXY header, and a connection whose SNI matches no route on a listener with no `*` fallback. None requires authentication to provoke, so opening connections in a loop turned a listener into a log amplifier against the operator's own disk and ingestion pipeline. Each is now a 10-second heartbeat via the new `internal/logthrottle`, which the HTTP boundary already used for malformed forwarding headers; the two conditions hold **separate** limiters so a peer provoking one cannot mask the other, and the limiters live on the listener rather than the route so a reload cannot reset them. Proven by `TestRouteMissLogIsThrottled`, where 50 unmatched connections emit 50 lines before the fix and 1 after. Backend dial failures are deliberately **not** throttled here: they report backend state rather than peer input, and suppressing them without a counter to replace them would trade this amplification for a blind spot during an outage. That needs a metric first and is tracked separately.

 `forwarded_headers` defaulted to `["forwarded", "x-forwarded-for"]` and derivation selects the first header *present* on the request, so RFC 7239 `Forwarded` outranked `X-Forwarded-For`. Trusting a proxy means trusting what it *writes*, but nearly every deployed proxy — nginx, HAProxy, Cloudflare, CloudFront, ALB, ingress-nginx — writes `X-Forwarded-For` and passes `Forwarded` through untouched. A client behind such a proxy could therefore send its own `Forwarded: for=…` and choose the canonical client address, defeating the boundary for CIDR authentication, IP rate limiting, WAF source matching, access logs, the FastCGI environment and the chain emitted upstream. Three changes close it: the default is now `["x-forwarded-for"]` alone; `forwarded_headers` is a **required** field once `trusted_proxies` is non-empty, so the headers a proxy authors are stated rather than inherited (`[]` remains available to keep peer-only identity); and `jul lint` warns when `forwarded` is enabled behind a trusted proxy. Derivation itself is unchanged — the boundary was never in the algorithm, it was in the default.

### Added
- **`jul lint` warns when server blocks sharing a `listen` disagree about a listener-scoped field (#258):** `read_header_timeout`, `read_timeout`, `write_timeout`, `idle_timeout`, `max_header_bytes`, `h2c`, `http3.enabled` and `http3.alt_svc_max_age` are resolved once per listen address, so a divergent value in a sibling block was silently discarded while the configuration parsed, validated and linted clean. ### Added

### Added
- **The HTTP reverse proxy now enforces `backend_tls` (#138):** `newProxyTransport` receives the resolved policy and builds its `TLSClientConfig` from it, so a private-CA backend, a backend client certificate, an SNI override and explicit peer identities all take effect for named upstreams and literal `https://` targets alike — including WebSocket and streaming upgrades, which are verified by the same policy rather than bypassing it. Policies are resolved while the handler generation is prepared, so unreadable or mismatched material aborts the reload instead of failing the first request. `ForceAttemptHTTP2` is retained, so HTTP/2 is still negotiated with a custom TLS config. A location's block overrides its pool's for that route; they are never merged.
- **Transport ownership follows the handler generation (#138):** each proxy handler owns its `http.Transport` and is staged into the generation, so a `backend_tls` change produces a new connection pool and a request admitted after the change cannot reuse a keep-alive or HTTP/2 connection established under the previous trust. The retiring generation closes its idle connections when it retires; requests already in flight finish on their own connection under the generation's existing drain contract. Proven by a test that warms a connection under one policy and shows the next generation refusing to reuse it.
- **Bounded backend-TLS failure categories (#138):** a handshake failure is logged alongside the proxy error as one of `unknown_authority`, `hostname_mismatch`, `peer_identity_mismatch`, `client_certificate`, `certificate_expired`, `certificate_invalid`, `tls_version`, `tls_handshake` or `tls_other`. The category is the whole payload — no host, address, certificate subject, SAN, file path or raw error text is derived from it — so it is safe to grep today and to count later. Documented in `docs/troubleshooting.md` with the fix for each.
- **No TLS downgrade on the data plane (#138):** a route configured for `https` refuses to dial a backend whose scheme is not `https`, so no retry, failover or discovery result can move a request from TLS to plaintext. The request fails instead, with an explicit reason.

### Added
- **`backend_tls`: one outbound trust policy for every backend client (#137, ADR 0016):** a new block under `[[upstreams]]` and `[[servers.locations]]` declares trust roots (`ca_file` with an explicit `ca_mode` of `system`, `system_and_file` or `file_only` — never inferred from the presence of a file), a client certificate for mutual TLS, the verified `server_name`, a `min_version` floor defaulting to 1.2, and explicit prefixed `peer_identities` (`dns:`, `uri:`). The new dependency-light `internal/backendtls` package resolves it into one immutable `Policy` that every consumer will share; `ClientConfig()` returns a fresh `*tls.Config` per caller, so a transport that sets `NextProtos` cannot affect another. Peer identities are ORed and checked through `VerifyConnection` — **after** Go's standard chain and hostname verification, never instead of it — so no configuration can use an identity check to skip validation. A discovery-returned address is a dial destination only: the configured logical name stays the verified identity, closing the registry-poisoning path where an attacker would otherwise choose both the address and the name it is checked against. The policy carries a content-based fingerprint (digesting the CA and client-certificate bytes, never the key) so a transport generation can be keyed by it, and a status-safe `Metadata()` projection that contains no path, no CA contents and nothing derived from the private key. Real TLS handshakes prove the behaviour: a private CA succeeds against the right name and fails against the wrong one, system roots reject a private CA, a matching identity passes, a non-matching one fails, and an identity alone does not rescue an untrusted chain.

### Added
- **Canonical inbound client address (#135, ADR 0016):** a new `[servers.client_address]` block declares which proxies may assert a client address — `trusted_proxies` (canonical CIDR prefixes or bare addresses), `forwarded_headers` (ordered preference over RFC 7239 `Forwarded` and `X-Forwarded-For`, defaulting to that order) and `max_hops` (default 16, maximum 255). The new dependency-light `internal/clientaddr` package is the single derivation: it parses the direct socket peer, ignores every asserted header unless that peer is explicitly trusted, selects at most one chain, walks it right to left discarding trusted hops, and takes the first untrusted valid address — or the leftmost address when the whole chain is trusted. Malformed, oversized, ambiguous, over-hop-limit, obfuscated (`for=_hidden`), `unknown`, hostname and invalid inputs fail **closed** to the transport peer with a bounded, rate-limited diagnostic that never contains the header value; no DNS lookup happens at any point. Prefixes must be canonical — `10.1.2.3/8` is rejected with the masked form in the message, so a typo cannot silently widen trust to a whole /8 — and `jul lint` warns when an entry covers the entire address space. The policy is classified `hot_reload` truthfully: it is compiled while the handler generation is prepared, so a malformed prefix aborts the reload before publish.

### Added
- **Inbound identity and backend peer-trust decision (#115, ADR 0016):** accepted one trust model covering five explicitly separate boundaries — the immediate transport peer, the proxy-asserted original client, auxiliary egress authorization, data-plane backend selection, and backend peer identity — and recorded why no generic "trusted" flag may span them, since each collapse maps to a known vulnerability class (header spoofing, destination authorization mistaken for peer authentication, discovery poisoning, transitive trust). Reusable named TLS profiles and a top-level `[[listeners]]` block are deferred with objective promotion triggers; the chosen per-server policy plus an identical-policy rule across servers sharing a listener is a lossless prefix of the listener block, so the deferral is not a one-way door. ## [1.0.0] – 2026-06-21

### Added
- First stable release of Jul.IA HTTP edge server.
- All foundation features declared GA — soak pending (see `docs/status.md`):
  - Core HTTP (static, proxy, FastCGI/uWSGI, vhosts, routing)
  - TLS + automatic HTTPS
  - Authentication (CIDR/Basic/JWT/forward-auth)
  - gRPC transcoding and passthrough
  - mTLS client auth
  - Console (operations cockpit)
- Full feature set with expanded descriptions:
  - Core HTTP server engine: static file serving, reverse proxy, FastCGI/uWSGI, virtual hosts, and routing (`exact`, `prefix`, `regex`).
  - TLS 1.2/1.3 termination with SNI certificate selection, HTTP→HTTPS redirect, and dynamic certificate selection at listener startup.
  - ACME automatic HTTPS (HTTP-01 and TLS-ALPN-01 challenges) with on-disk certificate cache and OCSP stapling — gated behind `acme` build tag.
  - mTLS / client certificate authentication with CA bundles, SAN verification, and CRL checking.
  - HTTP/3 over QUIC sharing TLS certificates, advertised via `Alt-Svc` — gated behind `http3` build tag.
  - h2c (cleartext HTTP/2) support for native gRPC clients without TLS.
  - gRPC-JSON transcoding (`grpc_transcode`) from compiled descriptor sets or server reflection — unary and streaming (server/client/bidi) with NDJSON and SSE framing modes — gated behind `grpc` build tag.
  - Native gRPC passthrough with trailers preserved and streaming frame flush — gated behind `grpc` build tag.
  - Two-tier response cache (memory L1 + optional disk L2) with TTL, `stale-while-revalidate`, Vary variant support, and admin purge endpoint.
  - Compression (gzip default; optional Brotli via `brotli` tag and Zstd via `zstd` tag) with Accept-Encoding negotiation, MIME allow-list, minimum size gate, and precompressed `.br`/`.gz` sidecar serving.
  - Token-bucket rate limiting keyed by client IP, request header, or JWT claim, with concurrent connection limiting per listener.
  - Authentication: CIDR allow/deny gates, HTTP Basic (bcrypt `htpasswd`), JWT bearer validation against JWKS endpoints (asymmetric only, `none` rejected), and forward-auth delegation.
  - WebAssembly plugin runtime via wazero with capability-gated KV store and outbound fetch, per-plugin memory/time limits, and panic isolation — gated behind `wasmplugins` tag.
  - L4 stream proxy (TCP/UDP) with TLS SNI passthrough routing and HAProxy PROXY protocol v1/v2 — gated behind `stream` tag.
  - Service discovery for upstream backends: DNS A/AAAA, DNS SRV (all builds), plus Consul and Kubernetes EndpointSlices behind build tags.
  - Web Application Firewall (WAF) with embedded OWASP Core Rule Set via Coraza — gated behind `waf` tag.
  - Secrets resolution (`${env:NAME}`, `${file:/path}`, `${secret:/path}`) with log redaction and `jul lint` detection of literal credentials.
  - Zero-downtime hot reload via SIGHUP, file watch, or admin API with generational handler swap, config preflight checks, and automatic listener rebinding.
  - Graceful shutdown with configurable timeout (default 30s).
  - Admin web console (`console` build tag) with live metrics dashboard, upstream health, certificate inventory, config history with one-click rollback, and setup wizard.
  - Prometheus metrics (`/metrics`) covering HTTP requests, cache events, compression, rate limiting, auth decisions, WAF events, upstream health, discovery errors, gRPC transcoding/proxy, plugin invocations, listener connections, stream connections, and certificate expiry.
  - OpenTelemetry tracing (OTLP gRPC/HTTP) with W3C tracecontext propagation, child spans for proxy, upstream, and cache operations — gated behind `otel` tag.
  - Structured logging (text/JSON) and pluggable access-log sinks (stdout, rotating file, syslog on Unix).
  - CLI: `jul lint` (validation + best-practice warnings, CI-friendly exit codes), `jul fmt` (canonical TOML rewrite), `jul run --serve/--proxy` (zero-config server), and `jul import nginx` (NGINX → TOML migration, gated behind `importer` tag).
  - NGINX config compatibility guide and migration example.
- Multi-architecture release binaries (Windows, Linux, macOS on amd64/arm64) in `lean` and `full` profiles.
- Docker image with distroless runtime.
- systemd and Windows service deployment assets.

- Request parsing hardening, header size caps, slowloris mitigation, HTTP/2 reset flood protection.
- Static file path traversal protection via `os.Root`.
- Admin listener loopback binding by default with bearer token authentication.
- Config snapshotting and audit logging for compliance.
